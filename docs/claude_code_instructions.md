# Mirror MVP 実装指示書（Claude Code向け）

## はじめに

このドキュメントは、Claude Code に Mirror（壁打ち用AIクローンサービス）の MVP 実装を依頼するための完全な指示書です。

**進め方の方針：**

- 初期セットアップ＋段階的型で進める
- このドキュメントを最初に全部読んでから、Phase 0（セットアップ）から開始
- 各 Phase 完了時に動作確認・コミット
- 不明点があれば必ず質問してから実装を進める

**重要な制約：**

- 推測で実装しない、不明点は必ず質問する
- 既存の決定事項を勝手に変更しない
- セキュリティに関わる部分は特に慎重に扱う

---

## 1. プロジェクト概要

### 1.1 サービス名

**Mirror（ミラー）**

### 1.2 サービスコンセプト

「忙しい本人の壁打ち相手を、分身させる」

特定の人物（クローン主）の判断パターン・経験・知識を学習させた壁打ち用AIクローンを作成し、それを許可した相手（メンバー）と共有することで、本人の時間を奪わずに思考整理・相談を行えるサービス。

### 1.3 重要な位置づけ

- **「判断するAI」ではなく「壁打ち用AI」**
- 答えを断定せず、思考整理を手伝う
- 必ず「最終的には本人に確認してね」のフッターを応答に含める

### 1.4 ユーザー構造

- **クローン主（Owner）**：自分のクローンを作って提供する人。月500円課金。
- **メンバー（Member）**：クローン主に招待されてクローンと対話する人。無料。

## 2. 技術スタック

### 2.1 確定スタック

- **フロントエンド**：Next.js (App Router) + TypeScript + Tailwind CSS
- **バックエンド**：Next.js API Routes
- **認証**：Google OAuth 2.0（NextAuth.js or 直接実装）
- **ストレージ**：Google Drive API（ユーザー所有のドライブ）
- **LLM**：Anthropic Claude API（@anthropic-ai/sdk）
- **決済**：Stripe Subscriptions
- **ホスティング**：Vercel
- **DB（認証情報のみ）**：Vercel Postgres or Supabase

### 2.2 重要な制約

- ユーザーのプロファイル・対話履歴は **Mirror のサーバに一切保存しない**
- 全ユーザーデータは **ユーザー自身の Google Drive** に保管
- Mirror サーバには認証情報・課金状態・招待コードのみ

## 3. アーキテクチャ

### 3.1 全体構成

```
┌─────────────────┐                ┌─────────────────┐
│   クローン主      │                │     メンバー       │
│  (Google認証)    │                │  (Google認証)     │
└────────┬─────────┘                └────────┬─────────┘
         │ OAuth                              │ OAuth
         ▼                                    ▼
┌─────────────────┐                ┌─────────────────┐
│ クローン主のGドラ │                │ メンバーのGドラ  │
│ ・APIキー        │                │ ・対話履歴        │
│ ・学習データ      │                │                  │
│ ・プロファイル    │                │                  │
│ ・メモ           │                │                  │
└────────┬─────────┘                └────────┬─────────┘
         │                                    │
         │      ┌──────────────────┐          │
         └──────│   Mirror本体     │──────────┘
                │  ・認証・課金    │
                │  ・処理層        │
                │  ・データ保持なし │
                └──────────────────┘
```

### 3.2 Mirror が持つもの・持たないもの

**持つ：**

- ユーザー認証情報（メアド、Google ID、表示名）
- 課金状態（Stripe 連携情報）
- 招待コード（ハッシュ化）
- メンバーとクローン主の紐付け

**持たない：**

- プロファイルデータ
- 対話履歴
- APIキー
- 学習データ
- ユーザーごとの個別URL
- 利用統計（同意なしには取得しない）

## 7. UI/UX 方針

### 7.1 デザイン方針

- ダーク基調、紫グラデーション系
- シンプル・ミニマル
- 「壁打ち相手」の温かみを感じさせる
- ※モックは旧アーキテクチャベース、新版は実装時に再構築

### 7.2 重要な UI 要素

- 対話画面に常時免責表示：「これは壁打ち用AIによる生成応答です。本人の判断とは異なる可能性があります」
- セットアップ進捗バー
- メモ機能のクイックアクセス

## 8. セキュリティ方針

### 8.1 必須対応

- HTTPS 必須
- Google OAuth 2.0 で認証
- APIキーは AES-256-GCM で暗号化、ユーザーパスワード由来鍵
- 招待コードはハッシュ化して DB 保管
- すべてのフォームに CSRF 対策

### 8.2 やってはいけないこと

- ユーザーデータをサーバ側に保存しない
- ユーザー同意なしにメトリクスを取得しない
- 平文の APIキーをログに出力しない

## 10. 完了確認・テスト

### 10.1 各 Phase 完了時の確認

- 機能が動作するか
- セキュリティ要件を満たすか
- エラーハンドリングが適切か
- UX が違和感ないか

### 10.2 全体完了時の E2E 確認

- 新規クローン主が登録 → セットアップ → 学習データ追加 → クローン作成
- 招待コード発行 → メンバー登録 → 対話
- メンバーがエスカレ → 本人が回答 → プロファイル更新
- 課金 → 14日試用 → 自動課金 → 退会
